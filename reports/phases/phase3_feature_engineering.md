# Phase 3 V1 - Series-Level Historical Feature Engineering

Generated by `scripts/phase3_reports.py`. Engine version `1.0.0` (`scripts/feature_engine.py`). No models were trained in this phase.

## 1. Architecture: reusable engine vs. dataset-specific orchestration

`scripts/feature_engine.py` is dataset-agnostic - it has no concept of "development", "Cologne", or Kaggle. It exposes:

- `build_features(store, team1, team2, prediction_time, best_of, tier)` - **read-only**, returns a matchup feature dict using only state strictly before `prediction_time`.
- `update_state(store, team1, team2, winner, ..., update_team1, update_team2, update_elo)` - mutates the store after a result is known.
- `process_chronological_stream(store, rows)` - the shared two-phase batch driver used by every orchestration mode, so Mode A/B/C can never diverge in their temporal-safety logic.

Three modes are supported by this same engine:

- **Mode A (implemented here)**: `scripts/build_series_features_v1.py` - batch-generates leakage-safe feature rows for every eligible development match.
- **Mode B (implemented here)**: `scripts/build_pre_cologne_snapshot.py` - runs a *fresh* store through the same full development stream, truncated to strictly before the first Cologne 2026 match, and saves a frozen snapshot for a future pre-event tournament simulation that never sees real Cologne results.
- **Mode C (future, not implemented)**: given a saved state (`StateStore.from_json`) and a future scheduled match, call `build_features()` once to get its pre-match features, hand them to a future model, and after the real result is known call `update_state()` once and continue. `tests/test_feature_engine.py::test_batch_vs_single_call_equivalence` proves Mode A's batch path and this one-match-at-a-time path produce identical feature vectors given identical prior history - training-time and future inference-time feature logic can never diverge because they are the exact same function calls.

## 2. Match identity

Every processed match carries `source` (`"kaggle_ektarr"` for the current Kaggle data), `source_match_id` (the provider's own raw match id - NOT assumed globally unique), and `canonical_match_uid = f"{source}:{source_match_id}"` (globally unique by construction). A future second data source (e.g. GRID, or manually curated rows) can be namespaced under its own `source` string and appended to the same stream without id collisions, even if its raw match ids happen to overlap numerically with Kaggle's.

## 3. ELO V1

Initial rating `1500.0` for every team. `E_A = 1 / (1 + 10 ** ((R_B - R_A) / 400))`. `K = 32.0` (fixed). `R_new = R + K * (S - E)`, `S=1` for the winner, `S=0` for the loser. Deliberately simple: no tournament-tier weighting, no BO1/BO3/BO5 weighting, no time decay, no margin-of-victory multiplier, no per-context K-factor. This keeps it interpretable and gives a transparent baseline strength feature; refinements are explicitly postponed (Section 8).

## 4. Beta(2,2) smoothing

`overall_win_rate_smoothed = (wins + 2) / (matches + 2 + 2)` - returns exactly 0.5 for a team with zero prior matches, and is used identically for the format-specific win rate (restricted to prior matches with the exact same `bestOf` as the current match, no bucketing beyond exact equality - so the engine supports any future BO value without special-casing).

## 5. Rolling windows and margin

`win_rate_last_5`/`win_rate_last_10` use up to the 5/10 most recent strictly-prior matches (fewer if less history exists; 0.5 with zero history). The signed series margin is `own_score - opponent_score` from the team's own perspective for that match (e.g. a 2-0 win is +2, a 1-2 loss is -1, a BO1 loss is -1) - `avg_series_margin_last_5`/`_last_10` average this over the same windows, 0 with zero history.

## 6. Cold-start handling

A team with no `TeamState` yet (never seen) gets: `elo_before=1500`, `overall_win_rate_smoothed=0.5`, `win_rate_last_5=0.5`, `win_rate_last_10=0.5`, `format_win_rate_smoothed=0.5`, `avg_series_margin_last_5/10=0`, `total_matches_before=0`, `matches_last_30_days=0`, `days_since_last_match=NaN` (never a sentinel like 999 - a downstream model must be able to tell "no history" apart from "played recently"). No future information is ever used to fill these in.

## 7. Timestamp batching (temporal safety)

Across the 9,662-row development stream, 1,587 exact-timestamp groups contain more than one match (4,312 matches total are affected). For every such group, `process_chronological_stream` computes features for **every** row in the group before applying **any** result from that group (see `tests/test_feature_engine.py` for the synthetic proof) - a match at time t never sees another match's result also timestamped t, and no match ever sees its own result. Within a group, both feature generation and state-update order use a deterministic secondary sort (`canonical_match_uid`) so a full rerun is byte-identical; true simultaneity between two matches sharing a team is inherently ambiguous, and applying updates in a fixed deterministic order is the documented, defensible choice made here rather than attempting to infer a "real" order that the data doesn't record.

## 8. Team identity policy

`data/interim/team_identity_policy.csv` mechanically applies the Phase 2.5 proposed decisions (no new manual judgments made here): 778/792 original team names are `identity_feature_eligible=1` (14 are not - 11 `MANUAL_REVIEW` + 3 `EXCLUDE_FROM_IDENTITY_DEPENDENT_FEATURES`, 0 `NEEDS_EPISODE_SPLIT`). A canonical name is eligible only if every original spelling mapping to it is eligible (conservative; only relevant to the `Magic`/`magic` merge today, both eligible, so no real conflict exists yet).

Of the 9,662 development matches, **206** have at least one identity-ineligible side and are **excluded from V1 feature rows** (`data/interim/phase3_identity_excluded_matches.csv`). Refined per the addendum: this does *not* mean those matches are entirely thrown away. **ELO is the only pair-dependent state component** - it requires trusting both ratings symmetrically, so it is skipped whenever either side is ineligible. The *eligible* side's independent state (win/loss record, rolling form, format record, margin history, activity/experience) still updates from such a match, since that side's own result is a real, trustworthy fact regardless of the opponent's identity status - the new `HistoryEntry` is just flagged `opponent_identity_trusted=False` so a future H2H/opponent-dependent feature can exclude it. The *ineligible* side never has any state tracked at all.

## 9. Why only difference features are intended for modelling

Phase 1/2 established that `team1`/`team2` are assigned by a per-match numeric-id sort with no home/away meaning, yet the reconstructed team1 win rate is a persistent ~55% (Phase 2.5's `orientation_analysis.md`: a real bias, correlated with a diagnostic strength proxy, consistent with an upstream ordering artifact, exact cause not established). Representing the matchup via `Team1 - Team2` difference features (plus side-symmetric confidence features) prevents a model from learning that spurious ordering signal instead of real relative strength. No mirrored augmentation or side-swapping is implemented in Phase 3 - only the *diff-feature representation* itself, which is a necessary but not sufficient step; train-time side balancing is deferred to the modelling phase (Section 11 documents the symmetry invariant this relies on).

## 10. Why Cologne is absent

`series_features_v1.parquet` is built exclusively from `evaluation_group == "development"` matches. Cologne 2026 and post-Cologne matches are never fed into `process_chronological_stream` for Mode A, and Mode B's frozen snapshot is further restricted to strictly before Cologne's first match (derived from `evaluation_manifest.csv`'s `cologne_2026` labels, not from the tournament name string, which is used only as a secondary sanity cross-check) - `scripts/validate_phase3.py` checks both independently.

## 11. Orientation-symmetry invariant (documented, not a data transform)

Given the *same* store state, swapping which team is passed as `team1` vs `team2` to `build_features` must (a) exactly negate every `*_diff` feature, (b) leave every symmetric confidence feature unchanged, and (c) would flip the target `1 - team1_series_win` if it were a real match result. `tests/test_feature_engine.py::test_side_symmetry_of_diff_and_confidence_features` proves (a)/(b) on synthetic state; (c) is a trivial arithmetic fact checked separately.

## 12. Evaluation model vs. future deployment model

- **Evaluation model** (Phase 4+, not built yet): trained and backtested strictly without Cologne, so Cologne stays a genuine, never-touched holdout for judging the approach.
- **Future deployment model** (later, not built yet): once an architecture/hyperparameter choice has been evaluated and permanently recorded, a separate deployment model may be retrained on *all* legitimately available historical data at that time, including Cologne and anything completed after it. The Cologne holdout restriction applies to model development and historical evaluation, not to the eventual deployed model - this prevents permanently discarding useful historical data once evaluation is complete.

## 13. Canonical match schema (minimum fields for a new future result)

The engine does not care whether a completed match came from Kaggle or another source. A new completed result needs at minimum:

```
match_id / source_match_id
datetime
team1_canonical
team2_canonical
bestOf
tier/context (if known)
score1_match
score2_match
```

Orchestration wraps this into the engine's required stream columns (`datetime, source, source_match_id, canonical_match_uid, team1_canonical, team2_canonical, best_of, tier, score1, score2, team1_win, team1_eligible, team2_eligible`) by adding `source`, deriving `canonical_match_uid`, and mapping scores/winner - exactly what `build_series_features_v1.build_stream_rows` does for the current Kaggle rows.

## 14. Future-prediction input contract (before a match starts)

**Required**: prediction datetime, Team A canonical identity, Team B canonical identity, BO format. **Optional/context**: tier, tournament. **Never required**: final score, map result, current-match statistics, or any other post-match information - `build_features` does not accept or need any of these. This is what makes the eventual prediction system usable before a real match starts, not just as a historical-backtest tool.

## 15. Cold-start future teams

An opponent never seen in the training data is handled automatically by the same cold-start defaults documented in Section 6 - `store.get(name)` simply returns `None` and `compute_team_features` falls back to the defaults. `both_teams_have_history`/`_5_matches`/`_10_matches` expose this to a downstream model so it can distinguish a brand-new opponent from an established one rather than silently treating them the same.

## 16. State versioning

Every saved `StateStore.to_json()` snapshot embeds `engine_version` (currently `1.0.0`), `n_matches_processed` (distinct `canonical_match_uid` count), and a caller-supplied `meta` block (cutoff datetime, source, mode, generation timestamp) - see `series_team_state_v1_full.json` (Mode A, full development state) and `pre_cologne_team_state_v1_full.json` (Mode B, frozen pre-Cologne state) for the two snapshots produced in this phase.

## 17. Deliberately postponed

Map-level features, player-level/roster features, ELO tuning (time decay, margin-of-victory, tournament-tier weighting, opponent-strength adjustment, per-context K), head-to-head features, veto/map-pick logic, mirrored/side-swap data augmentation, any Cologne evaluation or model inspection, and all model training/hyperparameter tuning. Nothing in this list is implemented or even prototyped in Phase 3.
