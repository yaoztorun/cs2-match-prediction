## 11. Target trustworthiness: is `team1_win` usable?

**No — see `reports/leakage_analysis.md` for the full analysis.** Summary: reconstructing the winner as `sign(score1_match - score2_match)` on the 9,923 series rows (1 missing score, 5 literal ties set aside) disagrees with the provided `team1_win` column in 4,952/9,917 rows (49.9%). `team1_win==1` fires in only 6.0% of series rows even though `score1_match > score2_match` is true in 55.1% of resolvable rows — it is correct 99.1% of the time when team2 truly wins but only 10.1% of the time when team1 truly wins. It is also internally inconsistent: it differs between a match's own series row and its map rows in 3,407/9,923 matches. **Reconstruct the label from scores; do not use `team1_win`.**

## 14. Open Questions Before Feature Engineering

These are flagged, not resolved, by this audit:

1. **`datetime` semantics** — assumed to be the scheduled/start time, but this is not verified against the data source. If it is instead a completion/scrape time, any chronological train/test split logic would need to change.
2. **Roster availability timing** — do the `team{1,2}_player{1-5}_id`/name columns reflect the pre-announced starting lineup (safe as a pre-match feature) or the post-hoc actual boxscore roster including substitutions (leaky)? Not distinguishable from the data alone; must be confirmed against the collection method.
3. **Team identity resolution** — `team_id` is confirmed non-persistent (unique per match); `team_name` is only a candidate key and has unresolved collisions (Section 9). This must be resolved — likely via a name-normalization + manual-review pass, or an external team-id mapping — before any ELO/rolling/head-to-head feature can be trusted.
4. **Tied/missing series scores** — 5 series rows have literal tied `score1_match`/`score2_match` and 1 row has a missing score. These need an explicit drop/adjudicate rule.
5. **Missing `bestOf`** — 116 series rows have a blank `bestOf`; needs a fallback (e.g. infer from map-row count, or drop).
6. **Blank map identities** — 39 map rows have a score but no `map_id`/`map_name`; decide impute vs. drop.
7. **Blank map rows** — 39 map rows have neither score nor map identity; decide whether these represent forfeits and how to encode that.
8. **`games_played` inconsistency** — disagrees with actual map-row counts in 56% of matches; decide whether to use it at all or always recompute from map rows.
9. **Tier provenance** — tier (1/2/3) is currently only recoverable from source filename; recommend materializing it as an explicit column during ingestion (this audit does so for its own analysis but the raw files are unchanged).
